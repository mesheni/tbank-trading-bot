# Аудит приложения tbank-trading-bot

## Краткое резюме

Проведён read-only аудит торгового бота T-Invest API. Приложение представляет собой **CLI-инструмент** (без графического интерфейса) с 5 подсистемами: исполнение сделок, ML/бэктест, CLI/отчёты, надёжность/безопасность, тестовое покрытие.

Выявлено **~40 уникальных замечаний**, из них:
- **Critical: 2** — рассинхронизация признаков при live-прогнозе и отсутствие сверки открытых заявок
- **High: 13** — проблемы с kill-switch, троттлингом уведомлений, market fallback, устаревшими данными, противоречивыми сообщениями, отсутствием обработки ошибок
- **Medium: 16** — отсутствие индикатора прогресса, рассинхронизация настроек, пропуск валидации, проблемы кодировки
- **Low: 7** — косметические несоответствия документации

Главный риск: **live-прогноз LightGBM использует признаки с задержкой на `horizon` баров** относительно цены решения. Это означает, что модель описывает рынок H баров назад, а решение принимается на текущей цене.

Графический интерфейс отсутствует. UI — только терминальный вывод, CSV/JSON/MD отчёты и email-уведомления.

## Замечания

### Critical

#### 1. Live-прогноз LightGBM использует устаревшие признаки
- **Компонент:** C2
- **Файлы:** `bot.py:276-292`, `features.py:42-98`, `models/registry.py:211-241`
- **Подтверждено:** Да (анализ кода; требуется проверка на синтетических данных)
- **Описание:** `build_features()` вычисляет forward-таргет (`close.shift(-horizon)`) и удаляет последние `horizon` строк (NaN). `bot.predict()` берёт `features.iloc[-1]` — последнюю строку усечённого DataFrame. Для горизонта H признаки описывают бар `N-H`, но цена решения — бар `N`. Модель прогнозирует доходность для бара, который на H баров старше текущей цены.
- **Влияние:** Сигналы модели не соответствуют моменту принятия решения. Для `horizon=1` задержка — 1 бар; для `horizon=4` — 4 бара.
- **Рекомендация:** Вычислять признаки для последнего бара без таргета (или с dummy-таргетом) и использовать их для live-прогноза. Добавить тест на совпадение индекса признаков и цены.

#### 2. Отсутствие сверки открытых заявок между итерациями
- **Компонент:** C1
- **Файлы:** `tbank/trader.py:104-152`
- **Подтверждено:** Да
- **Описание:** `_execute()` опрашивает статус заявки до 3 раз, затем отменяет при не-финальном статусе. Если отмена не удалась — только warning. На следующей итерации бот не знает о существующей открытой заявке и может поставить новую → двойная позиция.
- **Влияние:** Двойная экспозиция, неконтролируемая сделка.
- **Рекомендация:** Хранить список активных заявок; перед каждой новой итерацией проверять их статус через `GetOrders`. При обнаружении незавершённых — ждать или отменять.

### High

#### 3. Kill-switch сбрасывается при перезапуске
- **Компонент:** C1, C4
- **Файлы:** `bot.py:171-172, 525-543`
- **Подтверждено:** Да
- **Описание:** `_entries_allowed = True` инициализируется в `__init__`. При просадке флаг переключается на `False`, но не сохраняется. После перезапуска бот продолжает торговлю, игнорируя просадку.
- **Рекомендация:** Сохранять состояние kill-switch в файл (`reports/kill_switch`) или БД. При старте проверять наличие маркера.

#### 4. Общие ключи троттлинга BUY/SELL подавляют критические уведомления
- **Компонент:** C1
- **Файлы:** `bot.py:367, 376, 424, 436`, `notify.py:90-102`
- **Подтверждено:** Да
- **Описание:** Ключи `partial-fill:{ticker}` и `order-not-filled:{ticker}` используются и для BUY, и для SELL. Отклонённый BUY подавляет уведомление об отклонённом SELL (стоп-лоссе) на 30 минут.
- **Рекомендация:** Разделить ключи: `order-not-filled:buy:{ticker}` и `order-not-filled:sell:{ticker}`.

#### 5. ORDER_FALLBACK_TO_MARKET по умолчанию включён
- **Компонент:** C1, C4
- **Файлы:** `.env.example:102-105`, `tbank/api.py:340-380`
- **Подтверждено:** Да
- **Описание:** По умолчанию `ORDER_FALLBACK_TO_MARKET=1`. При отклонении лимитной заявки (HTTP 400) бот автоматически подаёт рыночную. В `MODE=real` это приводит к неконтролируемой сделке по рыночной цене.
- **Рекомендация:** Изменить дефолт на `0` в `.env.example`. Добавить runtime-guard: в `MODE=real` блокировать fallback независимо от настройки.

#### 6. Отсутствие проверки свежести данных свечей
- **Компонент:** C1, C4
- **Файлы:** `bot.py:185-201`
- **Подтверждено:** Да
- **Описание:** `refresh_candles` перехватывает все исключения и работает с кэшем из БД без проверки возраста. При недоступности API бот торгует на устаревших данных.
- **Рекомендация:** Добавить проверку: если последний бар старше `2 × loop_interval_sec` — приостановить торговлю и отправить уведомление.

#### 7. train_summary.json содержит невалидный JSON (NaN)
- **Компонент:** C2
- **Файлы:** `cli.py:336-348`, `reports/train_summary.json`
- **Подтверждено:** Да (файл содержит bare `NaN`)
- **Описание:** `json.dumps(payload)` с `allow_nan=True` записывает `NaN` — невалидный RFC-8259 JSON. Внешние инструменты (JavaScript, строгие парсеры) отклоняют файл.
- **Рекомендация:** Использовать `json.dumps(payload, allow_nan=False)` или заменить NaN на `null` перед записью.

#### 8. Рассогласование гейта качества модели между бэктестом и live
- **Компонент:** C2
- **Файлы:** `bot.py:254-274`, `cli.py:394-398`
- **Подтверждено:** Да
- **Описание:** Live `_model_allowed()` проверяет `directional_acc` и Sharpe. Бэктест не применяет этот гейт — результаты не сопоставимы.
- **Рекомендация:** Добавить в `cmd_backtest` предупреждение, если модель не прошла бы live-гейт.

#### 8a. Расхождение семантики исполнения между бэктестом и live
- **Компонент:** C2
- **Файлы:** `backtest.py:68-116, 118-162`, `bot.py:358-456`
- **Подтверждено:** Да
- **Описание:** Бэктест применяет `exec_price = price * (1 ± slip)` для покупок и продаж, но не симулирует partial fills, задержку исполнения/позицию в очереди, cancel-and-replace и единообразный учёт `commission_min_rub`. Live использует `avg_exec_price` из ответа брокера, который может существенно отличаться от расчётной цены.
- **Влияние:** Результаты бэктеста не отражают реальное качество исполнения и могут завышать или занижать ожидаемую доходность.
- **Рекомендация:** Добавить в бэктест модель частичных исполнений, задержки и минимальной комиссии, а также логировать расхождение расчётной и фактической цены в live.

#### 9. Противоречие между report и normalize
- **Компонент:** C3
- **Файлы:** `cli.py:613-618, 1075-1080`
- **Подтверждено:** Да
- **Описание:** `report` советует запустить `normalize` для вывода излишка, но `normalize` говорит, что вывод невозможен.
- **Рекомендация:** Исправить текст в `report`: заменить «излишек будет выведен» на «выполните reset-sandbox для полного сброса».

#### 10. reset-sandbox падает с EOFError без --yes
- **Компонент:** C3
- **Файлы:** `cli.py:1128-1132`
- **Подтверждено:** Да
- **Описание:** `input()` в не-TTY окружении выбрасывает EOFError → traceback вместо понятного сообщения.
- **Рекомендация:** Обернуть `input()` в try/except EOFError → вывести «Передайте --yes для неинтерактивного режима» и вернуться с кодом 2.

#### 11. main() без обработки исключений
- **Компонент:** C3
- **Файлы:** `cli.py:1216-1259`
- **Подтверждено:** Да
- **Описание:** Ошибки API, сети, конфигурации показывают raw Python traceback вместо понятного сообщения.
- **Рекомендация:** Обернуть dispatch в try/except: `APIError` → «Ошибка API: ...», `ConnectionError` → «Нет соединения», `ValueError` → «Конфигурация: ...».

#### 12. status показывает бюджет sandbox в real-режиме
- **Компонент:** C3
- **Файлы:** `cli.py:585-587, 786, 963-965`
- **Подтверждено:** Да
- **Описание:** `status` не вызывает `_budget_base_warning()`, в отличие от `report` и `digest`. Пользователь видит «бюджет 1 000 000» в real-режиме.
- **Рекомендация:** Добавить проверку `_budget_base_warning()` в `cmd_status`.

#### 13. Токен может попасть в коммит через .env.example
- **Компонент:** C4
- **Файлы:** `.env.example`, `.gitignore`
- **Гипотеза:** Если пользователь случайно вставит токен в `.env.example` и закоммитит — токен утечёт. Pre-commit hook отсутствует.
- **Рекомендация:** Добавить pre-commit hook или CI-проверку на наличие паттернов токена в tracked-файлах.

#### 14. smoke сообщает об успехе при частичном сбое
- **Компонент:** C3
- **Файлы:** `cli.py:170-175`
- **Подтверждено:** Да
- **Описание:** Сбой загрузки новостей логируется, но команда возвращает 0 и печатает «Smoke-тест пройден».
- **Рекомендация:** Возвращать ненулевой код при любом сбое; печатать «Smoke-тест пройден частично».

### Medium

#### 15. Нет подтверждения для MODE=real при запуске (severity High)
- **Компонент:** C1, C3 | `cli.py:465-482`
- **Подтверждено:** Да
- **Влияние:** Случайная смена `MODE=real` в `.env` запускает торговлю реальными деньгами без предупреждения.
- **Рекомендация:** Требовать `CONFIRM_REAL_TRADING=YES` (не интерактивно, чтобы работал systemd).
- **Статус:** исправлено (`cli.cmd_run` проверяет `CONFIRM_REAL_TRADING`).

#### 16. Тихий выбор счёта при отсутствии ACCOUNT_ID
- **Компонент:** C1 | `cli.py:117-124`
- **Подтверждено:** Да
- **Влияние:** В real-режиме с несколькими счетами (брокерский, ИИС) бот молча выберет первый и может торговать не на том счёте.
- **Рекомендация:** Требовать явный `ACCOUNT_ID` в real-режиме или предупреждать о выборе первого счёта.

#### 17. Оффлайн-команды обходят config.validate()
- **Компонент:** C1 | `cli.py:1150-1151, 1221-1225`
- **Подтверждено:** Да
- **Влияние:** Неверные risk-параметры (например, `STOP_LOSS_PCT=5`) проходят в backtest и дают недостоверные результаты.
- **Рекомендация:** Валидировать risk-параметры и для offline-команд (`train`/`backtest`/`status`/`send-test-email`).

#### 18. Нет индикатора прогресса для download/train
- **Компонент:** C3 | `cli.py:179-189, 262-349`

- **Рекомендация:** Добавить счётчик `[i/N]`, прошедшее время и оценку остатка.

#### 19. Digest без заметок о покрытии и дате в теме

- **Рекомендация:** Добавить дату в тему и строку о покрытии периода в тело письма.

#### 20. Непостоянство троттлинга: in-memory vs файл
